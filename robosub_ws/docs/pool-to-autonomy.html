Pool to Autonomy

A verified ROS 2 + Gazebo simulator for our AUV, and the path from “I installed ROS” to a sub that finds the gate on its own.

01

Start with what the machine actually is

Before any of this works, one assumption has to be corrected.

This desktop is not the Jetson. It is an x86_64 workstation — and it had no ROS on it at all. The Jetson Orin Nano is a separate box. That is good news: this machine is dramatically better at running simulation than an Orin Nano will ever be, so sim belongs here and the Jetson stays the vehicle computer.

Why the sim runs in a container

Ubuntu 24.04's native ROS 2 is Jazzy. The sub's Jetson runs Humble (JetPack 6 / Ubuntu 22.04). Running Humble in a container here means a node that works in simulation is the same node that runs on the vehicle — no distro mismatch discovered the week of competition.

02

The one thing blocking you

Everything renders on the CPU until this is fixed.

A kernel update landed without its matching NVIDIA module, so nvidia.ko cannot load and all 3D falls back to llvmpipe — software rendering. Gazebo still runs at real-time; it is the camera that suffers, managing about 10 FPS.

Running kernel6.14.0-35-genericno nvidia.ko
Previous kernel, still installed6.14.0-33-genericfull module set
Module / userspace version580.65.06 · both matchwill load
Secure Bootenabledsigned modules only

You do not need root for this. Kernel 6.14.0-33 is still installed and still has a complete, correctly-versioned NVIDIA module set. Boot into it and the GPU works.

Booting the working kernel

The GRUB menu is hidden on this machine (GRUB_TIMEOUT=0), and it boots in UEFI mode, so:

  1. Reboot.
  2. Press Esc repeatedly as soon as the firmware logo appears.
  3. Advanced options for Ubuntu → Linux 6.14.0-33-generic.
  4. Confirm with nvidia-smi.

This choice lasts one boot. The next restart goes back to the broken -35 kernel unless you pick -33 again.

This is a shared lab machine — administrator, curc, rmc and rud also have accounts on it. Check nobody is mid-run before rebooting.

The permanent fix needs an admin

Only administrator is in the sudo group. Ask them to run:

sudo apt update
sudo apt install -y linux-modules-nvidia-580-open-generic-hwe-24.04

That installs the module build for 6.14.0-35 and makes the fix survive reboots and future kernel updates.

Tell them not to switch to DKMS. Secure Boot is on and Canonical's prebuilt modules are already signed. DKMS-built modules would be unsigned and refuse to load — trading one broken driver for another.

03

Run the sub

The environment is built and verified at ~/robosub_ws.

cd ~/robosub_ws
./run.sh                              # enter the container
colcon build --symlink-install
source install/setup.bash
ros2 launch robosub_sim pool.launch.py

In a second terminal, ./run.sh again attaches to the same container. Drive the sub:

ros2 topic pub -r 10 /sub/cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 1.0}, angular: {z: 0.2}}'

ros2 topic echo /sub/odom            # where the sub thinks it is
rqt_image_view /sub/camera/image_raw  # what the sub sees

Measured on this machine, with the GPU still broken: real-time factor 1.0 · IMU 100 Hz · odometry 50 Hz · camera 10.3 Hz · cruise speed ≈ 1.3 m/s. The GUI opens and physics runs at full speed on the CPU alone — only the camera is waiting on the driver, so Phases 1–4 need no GPU at all.

04

How the pieces connect

One seam decides whether your code survives the move to the real sub.

05

Underwater navigation is not ground navigation

Most ROS tutorials teach a wheeled robot on a flat floor. Almost none of it transfers directly.

There is no GPS

Radio does not penetrate water. The sub never receives an absolute position fix. Everything you know about where you are is integrated from motion — and integration drifts.

Six degrees of freedom

A ground robot is x, y, heading. A sub is x, y, z, roll, pitch, yaw, and depth is something you actively hold, not something the floor holds for you.

Nav2 does not apply

Nav2 assumes a 2D costmap and a ground base. Borrow its ideas — behavior trees, recovery behaviors — but you will write the control and planning yourself.

Depth is your one certainty

A pressure sensor gives absolute depth that never drifts. It is the single most trustworthy number on the vehicle. Build your estimator around that anchor.

Drift is the whole problem

IMU and DVL dead reckoning accumulate error without bound. Vision against known objects — the gate, the buoys — is what resets it. That loop is the navigation system.

Thrusters are not wheels

Motion is produced by combining several thrusters at once. The mapping from “go forward and yaw” to individual forces is control allocation, and it lives in exactly one file.

The simulator publishes perfect ground-truth odometry on /sub/odom. Use it to check your work, and then be disciplined: a navigation system that consumes ground truth is not a navigation system. Phase 4 is where you stop.

06

The path

Each phase ends with something you can demonstrate in the pool world.

Phase 0now

See the pool, then get the GPU back

Launch with the GUI — it already works, at real-time factor 1.0. Fly the camera around, watch the sub bob, drag the gate somewhere else. Then reboot into kernel 6.14.0-33 so the camera stops crawling.

Done when nvidia-smi prints the GPU and the camera runs well above 10 Hz.
Phase 1~1 week

ROS 2, learned inside this sim

Nodes, topics, messages, tf2, ros2 bag, rqt_graph. Skip the abstract turtle tutorials — you have a real vehicle publishing real data. Write a Python node that subscribes to /sub/odom and prints depth.

Done when your own node drives the sub by publishing /sub/cmd_vel.
Phase 2~1 week

The vehicle model

Read pool.sdf line by line. Change the mass and watch the sub sink. Move a thruster and watch it spin. Understand why it is trimmed slightly buoyant.

Done when you can add a fifth thruster and update thruster_mixer.py to use it.
Phase 3~2 weeks

Closed-loop control

A PID that holds depth, then one that holds heading from the IMU. Right now open-loop cmd_vel drifts sideways — that is real, and it is the thing feedback exists to kill.

Done when the sub holds 2.0 m depth and a commanded heading while being pushed.
Phase 4~2 weeks

State estimation without cheating

Fuse IMU and depth in robot_localization's EKF. Publish your own estimate. Compare it against /sub/odom ground truth and watch the error grow — that is dead-reckoning drift, and now it is a number you can plot.

Done when control runs on your estimate and ground truth is only used for scoring.
Phase 5~2 weeks

Seeing the gate

Subscribe to the camera, threshold for the orange gate in HSV with OpenCV, find its centroid, publish a bearing. This is deliberately the same orange as the competition markers.

Done when a /gate/bearing topic tracks the gate as the sub moves.
Phase 6~3 weeks

Autonomy

A state machine or behavior tree: dive to depth → search by yawing → align on the gate bearing → drive through → report. Add failure recovery, because the run will not go to plan.

Done when the sub passes the gate with no human input, from a random start pose.
Phase 7ongoing

Onto the Jetson

Rebuild the same container for arm64, swap the bridge for real drivers, and run hardware-in-the-loop. Because both sides are Humble, your nodes move across unchanged.

Done when the autonomy node runs on the sub with the simulator feeding it sensor data.
07

Field notes

Each of these cost a debugging cycle while building the environment. They are commented in the world file too.

The sim dies the moment you apply real thrust

Symptom: stable at 5 N, dead within one second at 20 N, with ODE INTERNAL ERROR 1: assertion "aabbBound >= dMinIntExact". The cause is the quadratic angular damping terms — kPP, mQQ, nRR. Gazebo integrates hydrodynamics explicitly, so once the hull picks up angular rate those terms diverge and the pose goes to infinity. The fix is to drop them and use strong linear angular damping instead.

An IMU that publishes nothing

Declaring an <sensor type="imu"> is not enough. The Sensors system only drives rendering sensors — camera, lidar. Non-rendering sensors each need their own world plugin, so the IMU stays silent until you add gz-sim-imu-system. The topic exists the whole time, which is what makes it confusing.

Never use <plane> for collision

An infinite plane gives ODE an unbounded AABB. The pool floor is a large box instead.

Rootless Docker and the GPU

This machine runs Docker rootless, which normally breaks GPU passthrough. It works here because /etc/nvidia-container-runtime/config.toml already sets no-cgroups = true. If GPU access ever fails inside the container, check that line first.
